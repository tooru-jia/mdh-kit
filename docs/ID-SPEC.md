# ID 规范

> **这是 mdh 的核心契约。**
>
> 改了下面任何一条，产物就不能再叫 mdh 文档、不能用 `.mdh` 后缀。
> 判定方法见文末「怎么验证」——跑 `conformance/` 测试集。
>
> 版本：`1.0.0` · 随 `mdh-kit@1.0.0` 发布

---

## 一、ID 是什么

每个块在**解析阶段**获得一个 ID，用于人和 AI 指认同一个位置：

```
人：在渲染结果里点一块 → 看到 M2 → 复制 → 发给 AI
AI：在源码里按 M2 定位 → 精确改写
```

**ID 是坐标。** 这是 mdh 与普通 Markdown 的根本区别，所以它的生成规则必须所有人一致——两个人用不同规则产出的 `M2` 指的是两个地方，坐标就废了。

---

## 二、规则

### 规则 1：字母表示层级，只有 M / N / O 三段

| 层 | 字母 |
|---|---|
| 第 1 层 | `M` |
| 第 2 层 | `N` |
| 第 3 层及更深 | `O` |

**只有三个字母，不允许换。** 换 `A/B/C` 的实现不符合本规范——即使它内部自洽，也无法与别人的实现对话。

> **「第 1 层」指什么**：从**列表项**（`- 项`）算起，不是从 `***list` 算起。
> `***list` 是声明型容器，它自己占一个 ID，但**不占一层** ——
> 占号（能不能被选中）和数层（能套几层）是两件独立的事。

**层数最多 3 段，第 4 层起压回 `O` 池**（详见规则 6）：

```
M2-N1          第 2 层
M2-N1-O1       第 3 层
M2-N1-O2       第 4 层 —— 仍是 O 段，序号接着排，不是 P1
M2-N1-O3       第 5 层
```

### 规则 2：数字表示「同一父节点下的第几个」

从 1 开始，连续递增。

```
M1  M2  M3        ← 三个顶层块
M2-N1  M2-N2      ← 第二个顶层块下的两个子节点
```

**每个父节点下有自己独立的计数器。** `M1` 下的 `N1` 和 `M2` 下的 `N1` 互不相干。

这条是 ID 唯一性的**根本保证**：父子树怎么长，编号就怎么长，不同分支的号永远碰不到一起。

### 规则 3：两种块，两种编号

块分两类，编号规则不同。**判定依据是「这个块本身装不装内容」**：

| 类型 | 判定 | 块 |
|---|---|---|
| **声明型** | 块本身不装内容，只给内部元素提供容器语义 | `***list`、`***column`、slides 的页 |
| **内容型** | 内容隶属于块本身，块和内容是整体 | `***table`、`***math`、`***mermaid`、`***chart`、引用 `>` |

**声明型**：声明自己占一个号，内容是**平级**的下一段。

```
***list        M1      ← 声明
  - 项一        M2      ← 内容，与声明平级
  - 项二        M3
```

```
***column      M1      ← 声明
  左栏          M2      ← 栏，与声明平级
  右栏          M3
```

```
@page(slides)  M1      ← 声明
  第 1 页        M2      ← 页，与声明平级
  第 2 页        M3
```

**内容型**：内容进它的下一层。

```
***table       M1      ← 块本身
  head          M1-N1   ← 表头
  - 甲, 1       M1-N2   ← 数据行
```

```
> 引用正文      M1
  段落          M1-N1
```

**为什么这样分**：声明型块只是"语法包裹"，渲染出来没有独立形态（`***list` 渲染成 `<div>` + `<ul>`，页渲染成 `<section>`），
它的内容是读者眼里的主体，所以内容不该被压深一层。内容型块本身就是内容的一部分（表格的边框、引用的竖线），
内容隶属于它，所以要进一层。

### 规则 4：缩进表达归属

在 `***list` 块内，**顶格**写的块与列表项平级，**缩进**写的块成为上一项的子块。

```
***list          M1
  - 项一          M2
  ***table        M3    ← 顶格 → 与项平级
  - 项二          M4

***list-end
```

```
***list          M1
  - 项一          M2
    ***table      M2-N1 ← 缩进 → 项一的子块
  - 项二          M3

***list-end
```

| 写法 | 结果 |
|---|---|
| 顶格 `***table` | 与列表项平级（同一个计数器） |
| 缩进 `***table` | 成为上一项的子块（进它的下一层） |

> 缩进只在 `***list` 块内表达归属；块外的缩进不承担语义。

### 规则 4·补：列表里夹的块，编号跟着源码顺序

同一层里，列表项和块是**按源码出现位置**交错编号的，不是"项排完再排块"。

```mdh
***list
- 项一          ← 先出现

***table
head: a
- 1
***table-end    ← 夹在中间

- 项二          ← 后出现
***list-end
```

```
list    M1
  项一   M2
  table  M3    ← 按源码位置排在项一和项二之间
  项二   M4
```

**不能**排成 `项一 M2 / 项二 M3 / table M4` —— 那样 ID 顺序和页面呈现顺序就反了，
AI 按 ID 改「M3」时会改到读者眼里的另一块。

### 规则 5：列表项、表格行的编号

```
- 项一          M1
  - 子项        M1-N1
```

**写不写 `***list`，列表项的编号完全一样：**

```
***list        M1      ← 声明占一号
  - 项一        M2      ← 项与声明平级
  - 项二        M3
```

```
- 项一          M1      ← 裸列表：没有声明，项直接是父级的子集
- 项二          M2
```

裸列表的分组节点**不占号**——它只是容器，渲染时和首项是一体的。
列表项落在哪一层，只看它在文档结构里的位置，不看外面写没写 `***list`。

```
***table       M1
  head          M1-N1
  - 甲, 1       M1-N2
  - 乙, 2       M1-N3
```

**单元格不生成 ID。**

### 规则 5·补：分栏的栏

```
***column      M1
  左栏          M2
   段落         M2-N1
  右栏          M3
   段落         M3-N1
```

栏与分栏平级（都是声明型的内容），栏内内容进栏的下一层。

### 规则 6：超过 3 层压回 O 池

**只有 M / N / O 三段。** 第 4 层起不再加段，序号回落到**同一个 O 池**继续排：

```mdh
> 第一层
>
> > 第二层
> >
> > > 第三层，最深处
```

```
quote       M1
  paragraph M1-N1        第 1 层正文
  quote     M1-N2        第 2 层（子引用）
    paragraph M1-N2-O1   第 2 层正文
    paragraph M1-N2-O2   第 3 层（> > > 的内容）
```

**池的归属是「最近的那个两段父」**：`M1-N2` 下所有深层节点共用 `M1-N2-O` 前缀，
序号一路往上加，不会因为再深一层就中断或重来。

```
M2-N1        两段父
  O1         第 3 层
    O2       第 4 层（不是 P1）
      O3     第 5 层
```

**代价**：从 ID 看不出「O2 是 O1 的孩子」还是「O2 是 O1 的兄弟」——
这是有意的取舍：**只支持 3 层结构，再深就没有层级可言**。

> 想要更深的层级表达，得改成允许 `P`、`Q` 段，
> 那会破坏「只有三个字母」这条契约，不在 1.0 范围内。

### 规则 6·补：解析时一次性下发，不依赖渲染

**所有 ID 在 `parse(source)` 完成时就全部确定。**

❌ 不允许：渲染到某个块时才给它编号
❌ 不允许：ID 依赖渲染顺序、屏幕尺寸、DOM 状态

**理由**：AI 不渲染，它只读源码。如果 ID 要渲染后才存在，AI 就永远算不出坐标。

### 规则 7：表格的行有 ID，单元格没有

| 元素 | ID |
|---|---|
| 表格 | `M1` |
| 表头行 | `M1-N1` |
| 数据行 | `M1-N2`、`M1-N3` |
| 单元格 | **无 ID** |

渲染时单元格会带 `M1-H1C1` 这类复合标记，但**那是渲染层的显示标识，不是 AST 里的节点 ID**。

### 规则 8：分割线、目录这类「无内容块」也是独立块

```
正文        M1
---
            M2    ← 分割线自己占一个号
正文        M3
```

**不允许**把分割线当作前一个段落的属性。

## 三、编辑期间的 ID 规则

### 规则 9：已有块的 ID 一律不变

用户编辑（新增、删除、改写）时：

| 操作 | 已有块 | 新增块 |
|---|---|---|
| 改写内容 | **ID 不变** | — |
| 新增块 | **ID 不变** | 取「同层最大序号 + 1」 |
| 删除块 | **ID 不变** | — |

**编号会出现空洞**（`M1 M2 M5 M6`），这是正常的。

**为什么容忍空洞**：AI 可能已经记住了 `M5`。如果删掉 `M3` 后重排，`M5` 就变成了别的块，坐标立刻失效。**空洞只是难看，漂移是功能性损坏。**

### 规则 10：重新打开时重新解析

关闭再打开、重新加载文档 → 重新 `parse()` → 编号重新从 M1 连续排。

**所以 ID 的稳定性边界是「一次会话」。**

> 用户和 AI 的对话发生在一次会话内，这个边界够用。
> 跨会话时，人重新点一次块、拿到新 ID 即可。

## 四、不允许的做法

| ❌ | 为什么 |
|---|---|
| 换成 A/B/C 字母 | 跨实现无法对话 |
| 容器内重置层级 | 与规范不符，深度信息丢失 |
| 渲染时才分配 ID | AI 无法在不渲染的情况下算坐标 |
| 编辑后重排所有 ID | 已发出的坐标全部失效 |
| 给单元格发 AST 级 ID | 规范明确不生成 |
| 把分割线并进段落 | 块与段落混淆，编号错位 |

## 五、算法：解析建树，编号只做一次

### 为什么分成两步

```
源码 ──解析──→ 纯结构树 ──编号──→ 带 ID 的 AST
                （没有 ID）        （所有 ID 在此刻确定）
```

**解析阶段完全不碰 ID。** 它只决定「谁是谁的孩子」：

- 缩进决定归属（顶格的块是项的兄弟，缩进的是项的孩子）
- `@next-slide` 切成页
- `@next-column` 切成栏

**编号在树建完之后，遍历一次统一做。** 好处：

- 只有一套编号逻辑，不存在「解析时编一遍、切页时再编一遍」两套需要同步
- 加新语法只要建对树，编号自动正确
- 嵌套层数和编号互不耦合：层数由语法决定，编号由这一步按类型算

### 编号怎么走

从根往下递归，**每一步看当前节点是什么类型**，决定子节点排在哪：

```ts
function assignNode(alloc, node, parentId) {
  // ① 裸列表的分组节点：不占号，项直接排到 parentId
  if (node.type === 'list' && !node.explicit) {
    assignListContent(alloc, node, parentId);
    node.id = '';      // 它只是容器，不占位置
    return;
  }

  // ② 自己占一个号
  const id = alloc.next(parentId);
  node.id = id;

  // ③ 按类型分发子节点
  if (声明型) 子节点 → alloc.next(parentId)   // 平级
  else        子节点 → alloc.next(id)         // 下一层
}
```

**关键点：声明型的子节点用 `parentId`，不是 `id`。**
这就是「项与 list 平级」的实现方式——不为声明型多开一层计数器。

| 节点 | 走哪条 |
|---|---|
| `***list` / `***column` / `slide` | 子节点用 `parentId`（平级） |
| `***table` / 引用 / `***math` / `***mermaid` / `***chart` | 子节点用 `id`（进一层） |
| 裸列表分组节点 | 不占号，项直接排到 `parentId` |

### 计数器怎么存

**每个父 ID 一套独立计数器**：

```ts
seq: Map<parentId, 已用到第几号>
```

```
M1 的第一子节点 → seq['M1'] 变 1 → M1-N1
M1 的第二子节点 → seq['M1'] 变 2 → M1-N2
M2 的第一子节点 → seq['M2'] 变 1 → M2-N1   ← 和 M1 的账互不相干
```

这是 **ID 唯一性的根本保证**：不同分支的计数器完全隔离，物理上碰不到一起。

### 超过 3 段时的压缩

`alloc.next(parentId)` 里判断父级段数：

```ts
const depth = parentId ? idDepth(parentId) : 0;
// 父已到 3 段 → 子节点回落到两段父的 O 池，不再加段
const poolParent = depth >= 3 ? 前两段(parentId) : parentId;
```

因为「第 3 段」和「第 4 段以后」共用 `poolParent` 这一个计数器，
序号天然接着排，不会撞号，也不会出现 `P1`。

### 列表里项和块的交错

列表的 AST 里，项在 `children`、夹在中间的块在 `blocks`，是两个数组。
但源码里是交错的，所以编号前要**按源行位置合并**：

```ts
merged = [...项(带 itemPos), ...块(带 pos)].sort(by 位置)
```

否则会出现「项一 M2、项二 M3、table M4」这种和页面顺序相反的结果。

## 六、怎么验证

```bash
node conformance/run.mjs
```

输出：

```
13 / 13 通过
✔ 全部通过：这份实现的 ID 序列符合 mdh 规范
```

**不通过就是不符合规范**——不管实现者怎么解释。

也可以校验别人的实现：

```bash
node conformance/run.mjs --parse=./my-impl.mjs
```

`my-impl.mjs` 导出 `parse(source)`，返回 `{ ast }`。

## 七、这份规范的使用条款

「mdh」这个名称和 `.mdh` 这个后缀，**只允许通过 `conformance/` 全部用例的实现使用**。

不合规的实现：

- 不得自称 mdh
- 不得使用 `.mdh` 后缀
- fork 请改名（如 `xxx-mdh`）或换后缀
