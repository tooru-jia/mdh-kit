# mdh AST 契约

> **这是对外承诺**。任何 mdh 实现（官方或第三方）产出的对象，必须符合本文档。
> 语法定义见 `SYNTAX.md`，ID 生成规则见 [`ID-SPEC.md`](ID-SPEC.md)。
>
> 版本：`1.0.0`
>
> 本规范随 `mdh-kit@1.0.0` 发布，作为第一个正式版本。

---

## 一、这份契约解决什么

md 的问题是「语法统一，理解各异」——同一份 `.md`，各家解析出的结构不一样，导致渲染结果千差万别。

**mdh 要「理解也统一」**：只要源码相同，所有实现产出的对象必须相同。

本文档定义的就是那个「相同」。

---

## 二、总体结构

```
RootNode（文档根）
└─ children: BlockNode[]
```

每个节点都是对象，**共有两个字段**：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `type` | string | ✅ | 节点类型，取值见第四节 |
| `id` | string | ✅ | 对象 ID，规则见第三节 |
| `description` | string | ✅ | 内容概要，供人查看、供 AI 定位 |

---

## 三、对象 ID

### 3.1 格式

```
O{序号}                      顶层块
O{序号}-D{序号}              子节点（列表项、表格行、分栏的栏）
O{序号}-D{序号}C{序号}       单元格
O{序号}-H{序号}              表头行
O{序号}-H{序号}C{序号}       表头单元格
O{序号}-D{序号}-{序号}       父级下再嵌一层（分栏里的块）
```

**可以任意层嵌套**——分栏里放表格，表格行就是 `O5-D1-2-D1`。

示例（与官方实现一致）：

| 节点 | ID |
|---|---|
| 根节点 | `O0` |
| 第 1 个顶层块 | `O1` |
| 第 3 个块的第 1 个子项 | `O3-D1` |
| 第 4 个块的第 1 行第 2 列 | `O4-D1C2` |
| 分栏 `O135` 第 1 栏里的第 2 个块 | `O135-D1-2` |
| 该块的第 1 行 | `O135-D1-2-D1` |

正则（与 `schema/ast-1.0.json` 一致）：

```
^O(0|[1-9][0-9]*)((-(D|H)?[1-9][0-9]*)*(C[1-9][0-9]*)?)$
```

### 3.2 生成规则

- **按出现顺序编号**，从 1 开始；根节点固定为 `O0`。
- 子节点用 `-D{序号}`，单元格追加 `C{列号}`，表头用 `H`。
- **同一份源码，每次编译产出的 ID 完全相同**（确定性）。
- ID 由编译器生成，**不写回源码**。

### 3.3 稳定性声明（重要）

> **ID 不保证跨编辑稳定。**

增删块后重新编译，**后面的块 ID 会顺延变化**：

```
编辑前              插入一段后
O1 标题             O1 标题
O2 列表             O2 新段落   ← 新占 O2
O3 表格             O3 列表     ← 原 O2
                    O4 表格     ← 原 O3
```

**因此 ID 只能用于「当场指认」**（如选中一块、复制给 AI 立刻修改），**不能当作长期引用的标识**。

如果将来需要持久标识，另行引入机制，不改变本文档定义的 ID。

### 3.4 各节点的 ID 形态

| 节点 | 形态 | 说明 |
|---|---|---|
| 根节点 | `O0` | 固定 |
| 顶层块 | `O1`、`O2` | 按顺序编号 |
| 列表项 | `O1-D1`、`O1-D2` | |
| 表格行 | `O1-D1`、`O1-D2` | 数据行 |
| 表格单元格 | `O1-D2C3` | 行 + 列 |
| 表头行 | `O1-H1` | 表头用 H |
| 表头单元格 | `O1-H1C2` | |
| 分栏的每一栏 | `O1-D1`、`O1-D2` | |
| Mermaid 节点 | `O1-A` | 用源码里写的节点 ID |
| slides 的每一页 | `O1-D1` | |

## 四、节点类型（必选清单）

**实现必须使用以下 `type` 名称**，不得自创别名。

| `type` | 对应语法 | 关键字段 |
|---|---|---|
| `root` | 整篇文档 | `children` |
| `heading` | `# 标题` | `level`、`text` |
| `paragraph` | 正文段落 | `lines` |
| `list` | `- ` / `1. ` / `***list` | `ordered`、`children` |
| `listItem` | 列表项 | `marker`、`ordered`、`lines`、`children` |
| `table` | `***table` | `headers`、`rows` |
| `tableRow` | 表格行 | `cells`、`cellIds` |
| `column` | `***column` | `ratios`、`columnBlocks`、`columnIds` |
| `math` | `***math` | `latex`、`name` |
| `chart` | `***chart` | `chartType`、`headers`、`rows` |
| `mermaid` | `***mermaid` | `source` |
| `code` | ` ``` ` | `lang`、`title`、`content` |
| `page` | `@page(slides)` | `preset`、`slides` |
| `slide` | `@next-slide` 切分出的页 | `index`、`children` |
| `quote` | `>` 引用块 | `children`（引用内的块） |
| `block` | 未专门建模的块 | `blockName`、`params`、`lines` |

### 通用约定

- **`name`**：块头部 `name="值"` 的值，可选。用于 `@名字` 引用。
- **`params`**：位置参数数组，如 `***column(1fr/2fr)` → `['1fr', '2fr']`。
- **`caption`**：题注文字，唯一会显示给读者的参数。

### 对象不携带编号

**`表(1)`、`图(1)`、`式(1)` 这类编号不在对象里。**

| 层 | 负责什么 |
|---|---|
| 解析 | 记录**引用关系**：`@员工薪资` 指向哪个对象（靠 `name`） |
| 渲染 | 按对象出现顺序**算出编号**，并把引用替换成「表(1)」 |

理由：编号是**呈现产物**，不是文档结构。把它写进对象会带来两个问题：

1. 改对象（增删块）后必须重算，否则编号错乱
2. 第三方实现必须算出**一模一样**的编号，才能让两份 AST 相等——这让呈现规则污染了结构契约

因此：**AST 里只留 `name`，不留 `number`。**

## 五、确定性要求

**同一份 `.mdh` 源码，任何合规实现必须产出完全相同的对象**（除 `id` 的编号须一致外，字段顺序不限）。

判定方式：

```
输入 .mdh → 实现 A → 对象 A'
输入 .mdh → 实现 B → 对象 B'
A' 必须等于 B'
```

**这是 mdh 区别于 md 的根本**：md 从没定义过「同一份 md 该解析成什么」，mdh 定义了。

## 六、一致性测试

任何实现都可以用下面的方式自证合规：

```
conformance/
├── cases/
│   ├── 001-heading.mdh    输入
│   ├── 001-heading.json   期望的对象
│   ├── 002-table.mdh
│   ├── 002-table.json
│   └── ...
```

**跑法**：读 `.mdh` → 编译 → 与同名 `.json` 逐字段比对。

**状态**：用例集在 [`../conformance/`](../conformance/README.md)。

## 七、JSON Schema

**契约不只是文字，还有机器可校验的 schema。**

| 文件 | 用途 |
|---|---|
| [`schema/ast-1.0.json`](../schema/ast-1.0.json) | JSON Schema 2020-12，可校验任何实现产出的对象 |

**校验方式**：

```bash
# 校验内置样例
node tools/validate-ast.mjs --sample

# 校验某个 .mdh 文件编译后的结果
node tools/validate-ast.mjs 你的文档.mdh

# 校验已有的 JSON 文件
node tools/validate-ast.mjs ast.json
```

**任何实现都应通过这个 schema**——这是「理解统一」的机器化保障。

### 已知的校验行为

- 用 `oneOf` 区分节点类型，因此**整体校验失败时，错误信息会列出所有不匹配的分支**。定位具体问题时，按 `type` 分组校验更直接（见 `tools/debug-schema.mjs`）。
- ID 正则允许任意层嵌套，与实现一致。

## 八、当前未覆盖（待补）

| 项 | 说明 |
|---|---|
| 行内格式的表示 | 加粗、斜体等在节点里如何表达（现在是渲染时再解析） |
| 元信息 `meta` | 已在实现里，schema 已覆盖，但文档未展开 |
| 错误与降级 | 遇到非法语法时，节点应该长什么样 |

### 往返保真度（已定）

`serialize(parse(src))` 再 `parse` 一次，**语义必须一致**，但以下字段允许不同：

| 字段 | 原因 |
|---|---|
| `columns` | 每栏的原始文本，仅供调试，重排后自然不同 |
| `blankBefore` | 渲染间距提示，往返后可能变化，不影响语义 |

**其余所有字段必须严格一致**，包括 `id`、`type`、`name`、`caption`、`lines`、`children` 等。

---

## 八、与实现的关系

本文档是**契约**，不是实现指南。

- 官方实现（`mdh/packages/parser`）目前**符合本契约**。
- 第三方可以用任何语言实现，只要产出相同的对象。
- 字段顺序、内部数据结构不作要求，**只要求字段名与语义一致**。
